# 语义切片增强方案总览

> 文档状态：方案计划，仅供评审。本文及同目录计划不包含任何代码改动。

## 1. 结论

当前项目的切片链路已经具备“结构识别 + 正文语义切片 + 表格/代码原子切片”的基础：

- `StructuredSegmenter` 按 Markdown 表格和围栏代码块拆分 `PROSE`、`TABLE`、`CODE`。
- `SemanticTextSplitter` 对正文按句向量相似度合并，对表格和代码按行边界打包。
- `CleaningTextSplitter` 统一补充 `block_type`、`code_lang`、`chunk_index`、`chunk_total`。
- `DocumentService` 目前只按 `doc_md5` 判断是否重复导入。
- `ChatConfig` 中相似度阈值、最小长度、最大长度仍硬编码为 `0.7 / 50 / 1000`。
- 现有检索日志出现过单次 `topK=8` 召回耗时约 `3.6s` 到 `8.6s`，说明切片质量、召回量和嵌入成本都需要一起观测。

建议不要一次性重写切片器。更稳妥的工程路线是先建立可评测、可重建、可回滚的版本化基线，再依次增强标题结构和边界算法，最后再引入父子分块。四个计划可以独立评审，但推荐实施顺序如下：

1. `semantic-chunking-01-versioned-baseline.md`
2. `semantic-chunking-02-heading-aware.md`
3. `semantic-chunking-03-adaptive-boundary.md`
4. `semantic-chunking-04-parent-child-retrieval.md`

## 2. 现状约束

| 项目    | 现状                                                                               | 对本方案的影响                                          |
|-------|----------------------------------------------------------------------------------|--------------------------------------------------|
| 文档格式  | 当前导入入口只接受 `.txt`，但正文允许 Markdown 标题、表格、代码围栏                                       | 标题和父级结构需要通过文本规则解析，不能依赖 PDF 解析器                   |
| 主链路   | `DocumentService -> CleaningTextSplitter -> SemanticTextSplitter -> VectorStore` | 新能力应尽量落在现有清洗和切片边界内，避免改写问答主链路                     |
| 切片元数据 | 只有文件、MD5、块类型、代码语言和切片序号                                                           | 需要补充策略版本、稳定 ID、标题路径和父子关系                         |
| 重复导入  | `doc_md5` 已存在即跳过                                                                 | 仅修改切片算法后重复上传同一文件不会重建索引，必须纳入版本化设计                 |
| 配置    | `0.7 / 50 / 1000` 硬编码在配置类中                                                       | 调参无法灰度，也无法按环境或实验策略切换                             |
| 测试    | 当前仅有一个 Spring 上下文加载测试                                                            | 切片逻辑需要引入纯单元测试和固定小语料回归                            |

## 4. 各方案边界

### 方案 01：切片版本化与评测基线

解决“算法改了但索引没有更新、效果好坏无法比较”的基础问题。内容包括：

- 将所有切片参数外置到 `rag.chunking.*`。
- 为切片写入 `chunk_pipeline_version`、`chunk_strategy`、`chunk_id`。
- 重建同文件索引时允许安全替换旧版本，而不是被 `doc_md5` 永久跳过。
- 建立固定小语料和离线指标，至少统计块数、平均/最大长度、碎块率、召回命中位置。

不在本方案中改变切片算法，因此可以独立上线。

### 方案 02：标题与章节感知

解决“正文、标题、列表混在一起，切片不知道自己在哪一章”的问题。内容包括：

- 解析 Markdown ATX 标题 `#` 到 `######`，生成标题栈。
- 分段和切片元数据携带 `section_path`、`section_level`、`section_id`。
- 切片合并时禁止跨一级章节直接合并。
- 表格和代码切片保留所属章节路径。

不引入 PDF 目录、OCR 或外部 NLP 服务。

### 方案 03：自适应边界与窗口策略

解决固定 `0.7` 阈值在不同文档上不稳、容易产生 `50` 到 `120` 字碎片的问题。内容包括：

- 计算相邻句相似度序列，而不是只和上一句比较后才决定。
- 在固定下限和上限之间，使用分位数和长度惩罚选择断点。
- 对边界附近的句子提供有限 overlap，避免答案线索正好落在切口两侧。
- 配置保留回退路径，策略异常时可切回旧贪心算法。

不改变 Milvus 索引结构和接口返回格式。

### 方案 04：父子分块与检索扩展

解决“子块精确召回但上下文不足”的问题。内容包括：

- 以章节或语义段为父块，以现有局部语义块为子块。
- 子块元数据保存 `parent_id` 和 `parent_text`。
- 检索后按父块去重，再将父块正文放入 prompt。
- 保留现有 `Reference` 字段，扩展返回中的父级定位信息。

这是增强幅度最大、改动面也最大的方案，适合在前三个方案稳定后实施。

## 5. 推荐组合顺序

### 第一阶段：先让切片可比较

实施方案 01。验收标准：

- 同一文件在同一策略版本下重复导入只返回“已存在”，不会重复写向量。
- 同一文件在策略版本升级后可重建索引。
- 固定测试集能输出块数、长度分布和碎块率。

### 第二阶段：加入文档结构

实施方案 02。验收标准：

- 每个正文、表格、代码切片都有可读的 `section_path`。
- 标题层级变化处不会被旧算法合并成同一块。
- 现有问答接口字段保持兼容。

### 第三阶段：优化边界质量

实施方案 03。验收标准：

- 固定语料上的 `p50` 块长度提升，且最大块不超过配置上限。
- 跨主题合并样本数下降，碎块率不高于基线。
- 可通过配置一键回退到旧贪心策略。

### 第四阶段：补足长上下文

实施方案 04。验收标准：

- 检索后按父块去重，重复父块不会重复占用 prompt。
- 命中子块时，模型拿到该子块所属父块正文。
- 对固定问题的答案覆盖率高于仅返回子块基线。

## 6. 统一验收原则

所有方案实施时共同遵守以下原则：

- 不删除现有 `SemanticTextSplitter.apply()` 对外行为，先保留兼容入口。
- 新策略必须能通过配置关闭，关闭后回到当前行为。
- 切片策略变化必须提升 `chunk_pipeline_version`，并触发重建。
- 单元测试不得依赖真实 LM Studio、Milvus 或网络，使用假的 `EmbeddingModel`。
- 端到端验证可以依赖本地服务，但必须与单元测试分开记录。
- 任何方案上线前都要保存旧集合或旧版本数据，确保可以回滚。

## 7. 评审建议

若目标是尽快改善当前 `jmu新生手册.txt` 的召回质量，建议先批准并实施方案 01 和 02。若当前最痛的问题是召回内容短、答案线索被切断，则应直接优先方案
03。方案 04 适合作为后续能力建设，不建议第一个落地。
